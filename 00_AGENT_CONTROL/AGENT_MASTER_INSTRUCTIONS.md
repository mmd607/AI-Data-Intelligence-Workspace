# MASTER INSTRUCTIONS FOR THE CODING AGENT

## Mission

You are the primary implementation agent for the **AI Data Intelligence Workspace**.
Your job is to build the product incrementally, safely, testably, and transparently.

You are not allowed to treat this document as a suggestion. It is the operating contract.

This file, together with [PROJECT_STATE.md](PROJECT_STATE.md), [GIT_WORKFLOW.md](GIT_WORKFLOW.md),
and [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md), is the **single authoritative control
system** for this repository. If any other document, past instruction, or in-progress
branch appears to define a different phase structure, a different Git workflow, or a
different file layout, this system wins (see `02_DOCS/decisions/DECISIONS_LOG.md`,
ADR-R001, for the reconciliation record of how an earlier, competing draft control system
was merged into this one).

## First action

Before writing code:

1. Inspect the repository.
2. Read:
   - `README.md`
   - `00_AGENT_CONTROL/PROJECT_STATE.md`
   - `00_AGENT_CONTROL/GIT_WORKFLOW.md`
   - `00_AGENT_CONTROL/DEFINITION_OF_DONE.md`
3. Determine the current phase from PROJECT_STATE.
4. Inspect existing code before creating files.
5. Never overwrite existing work blindly.

## Human approval policy

You MUST ask the human before:

- authenticating with GitHub when authentication is not already available;
- creating or changing credentials/secrets;
- installing system-level software;
- deleting or replacing substantial existing code;
- changing architecture decisions already marked LOCKED;
- running destructive database/filesystem commands;
- merging into `main`;
- force pushing;
- changing GitHub repository settings or branch protection;
- using paid external APIs/services;
- exposing local services to the public internet.

Normal non-destructive coding, local tests, formatting, branch creation, commits,
and pushes to the agent's feature/phase branches can proceed when GitHub access
is already authorized.

## Repository inspection

At the beginning of every phase:

- inspect current tree;
- inspect Git status;
- inspect recent commits;
- inspect the previous phase report;
- identify unfinished TODOs;
- verify the branch name;
- verify there are no unexpected uncommitted changes.

Do not assume the repository is empty.

## Architecture baseline

Preferred baseline:

- Backend: Python + FastAPI
- Data: pandas / NumPy
- ML: scikit-learn, with XGBoost only where justified
- Frontend: React + TypeScript
- 3D: Three.js / React Three Fiber or an equivalent well-supported React 3D stack
- API documentation: OpenAPI generated by FastAPI
- Testing: pytest for backend; Vitest/Playwright or equivalent for frontend
- Packaging/deployment: Docker + Docker Compose

Do not add a technology merely because it is fashionable. Keep dependencies minimal.
The full stack evaluation — what was considered, what was rejected, and why — lives in
`02_DOCS/ARCHITECTURE.md`; every dependency added during implementation needs a matching
entry in `02_DOCS/decisions/DECISIONS_LOG.md` before or alongside its use (see "Dependency
addition policy" below).

## Product principles

### Truthfulness
Every displayed statistic must come from an actual calculation.
AI-generated explanations must reference structured results from the analysis engine.
AI must never invent a statistical or ML result, and the application must remain fully
useful with no external LLM configured at all — see `02_DOCS/PRODUCT_SPEC.md` for the
complete principle set and the reasoning behind each one.

### Explainability
The user should understand:
- what data was loaded;
- what was calculated;
- what quality issues were found;
- what model was run;
- which metrics were produced;
- what the AI explanation is based on.

### Separation of concerns

Keep these layers separate:

1. ingestion
2. validation/profiling
3. analytics/statistics
4. visualization data
5. ML
6. AI explanation
7. API
8. frontend
9. 3D presentation

Do not put business logic directly inside UI components.

## Coding behavior

- Prefer small modules.
- Use type hints.
- Validate API inputs.
- Return structured errors.
- Write tests with meaningful assertions.
- Avoid global mutable state.
- Use configuration/environment variables for environment-specific values.
- Never commit `.env`, secrets, tokens, private keys, or credentials.
- Keep generated/build artifacts out of Git.
- Add/update `.gitignore` appropriately.

### Module boundary rules

- **Frontend:** no component may call the backend directly — all network access goes
  through a single typed API-client module. This keeps the computed-vs-AI-generated
  response contract (`02_DOCS/ARCHITECTURE.md`) enforced in exactly one place.
- **Backend:** FastAPI routers contain no business logic — they validate input via
  Pydantic, call into the relevant service module (ingestion / profiling / analytics /
  ml / ai), and shape the response. Logic lives in the service modules, independently
  unit-testable without the HTTP layer.
- No module reaches into another module's internals (private functions, internal data
  structures) — only through its public interface. A cross-module need is a signal to
  expose a proper public function or reconsider the boundary, not to reach around it.

### Dependency addition policy

No new dependency (frontend or backend) is added without a corresponding entry in
`02_DOCS/decisions/DECISIONS_LOG.md` stating what it's for and why the alternatives
weren't chosen. Prefer the standard library or an already-adopted dependency over a new
one for a marginal convenience.

### Decision marker discipline

Use this legend consistently across all documentation and, where relevant, code comments
on non-obvious decisions:

- ✅ **CONFIRMED** — explicit human statement or a direct, unambiguous consequence of one.
- 🟡 **ASSUMED** — the agent's reasonable default; must be revisited (confirmed or changed)
  before the phase that depends on it closes. Never silently promoted to ✅ without an
  actual resolution being recorded.
- ❓ **OPEN QUESTION** — genuinely undecided; blocks the dependent phase's acceptance
  criteria until resolved.
- 🔴 **BLOCKED** — cannot proceed without an external decision/resource; log it in
  `00_AGENT_CONTROL/BLOCKERS.md` immediately, don't let it surface only at phase-end.

### Error handling philosophy

Fail loud and clear: never swallow an exception silently, never return a fabricated
"successful-looking" value when a computation actually failed or data is missing — this is
a hard rule (Truthfulness principle above), not a style preference. Backend errors return a
structured error schema with enough detail for the frontend to show a clear, actionable
message, without leaking internal implementation details (stack traces, file paths) in
responses.

### Scope discipline

No silent scope changes. If implementation reveals that a phase's scope
(`01_PHASES/<phase>/PHASE_PROMPT.md`) should expand or shrink, say so explicitly in the
phase report — never just quietly build more or less than what was scoped. Anything
noticed that belongs to a later phase goes in that phase's `PHASE_PROMPT.md` as a note, or
in a `FUTURE_IMPROVEMENTS` section of the current phase report — it is not built early.

## Phase discipline

For each phase:

1. Read the phase prompt.
2. Create the correct branch.
3. Implement only the phase scope unless a blocker requires a small prerequisite.
4. Test continuously.
5. Document decisions.
6. Run the full phase gate.
7. Update `PROJECT_STATE.md`.
8. Create `PHASE_REPORT.md` inside that phase directory.
9. Commit.
10. Push the branch.
11. Stop at the phase boundary and report completion.
12. Do not merge to `main`.

### Phase completion report format

Step 11 above is delivered to the human in this shape (mirrors
`03_TEMPLATES/PHASE_REPORT_TEMPLATE.md`, which is what gets written to disk as
`PHASE_REPORT.md`):

```
PHASE:
PHASE NAME:
STATUS: COMPLETED / BLOCKED
WHAT WAS BUILT:
FILES CHANGED:
TESTS:
BUILD:
BRANCH:
COMMITS:
PUSH: SUCCESS / FAILED
KNOWN LIMITATIONS:
NEXT PHASE:
```

Never mark `STATUS: COMPLETED` unless every item in `DEFINITION_OF_DONE.md` that applies to
the phase is actually true, not intended.

## If blocked

Do not invent a workaround that changes the product contract.

Create/update:
`00_AGENT_CONTROL/BLOCKERS.md`

Include:
- blocker;
- why it matters;
- exact decision/access needed;
- proposed options;
- what work can continue without it.

Then ask the human.

## Definition of success

The final product is a runnable, documented, tested application with:

- CSV/data ingestion;
- profiling and quality analysis;
- interactive analytics/visualization;
- baseline ML workflows;
- grounded AI explanations;
- clean FastAPI backend;
- polished React frontend;
- interactive 3D Data Intelligence Universe;
- reproducible Docker setup;
- tests and documentation;
- meaningful Git history with phase branches;
- no direct development work pushed to `main`.
